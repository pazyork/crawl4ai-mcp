### 3.2 search benchmark (8 engines × 2 queries)

修复后所有 16 次 search 都返回了至少 4 条结果（修复前完全一样的配置下，海外引擎全失败、用户指定 engine 不生效）。最重要的差异：

- **结果 URL 不再是跳转链**（被 unwrap 后是真实 csdn/github/arxiv/ithome 等域名）
- **`requested_engine` 字段告知用户原始请求**（如 requested=duckduckgo，actual=baidu）
- **`fallback_engines_tried` 结构化列出每个失败的引擎和原因**

但**search 平均耗时上升**：从修复前 ~10s 到修复后 ~20s。原因：unwrap_redirect_urls 串接的 redirect 解码（百度对每条结果都需要请求一次目标页拿真实 URL）。当前用 8 并发 + 8s 总超时。可接受，但有优化空间（见 §6）。

## 5. 性能基线（修复后）

### 5.1 fetch 耗时分布

```
< 10s:  3 条 (GitHub releases, openrouter, obsidian)
10-20s: 5 条 (GitHub repo, dario, bestblogs, BV, PH 真实 blocked)
20-35s: 4 条 (medium, chatgpt, BV1CHQDYHEsU, youtube)
> 60s:  2 条 (claude docs 抖动, weixin 抖动)
```

主要时间消耗：
1. **代理冷启动 + Playwright TLS handshake**：1.5–3s
2. **域名特定 wait_for + 模拟用户行为**：5–15s
3. **强 fallback 路径（magic + simulate_user）**：仅 #4 GitHub 和 #5/6 PH 触发，加 ~5s
4. **视频字幕路径**：yt-dlp 子进程 8–25s

### 5.2 search 耗时分布

```
8-12s:   纯 baidu 命中（不 unwrap 跳转）
15-25s:  涉及 unwrap_redirect_urls 的请求
25-30s:  fusion 模式涉及多个海外引擎全失败
```

每条 redirect unwrap 现在 5s/请求 + 8 并发，最坏情况 5×N/8 秒。

### 5.3 验证 stderr 安静

修复前一次 fetch 产生约 5–8 行 `[FETCH]/[SCRAPE]/[COMPLETE]`。修复后 verbose 默认 False：
```bash
$ crawl4agent fetch ... 2> /tmp/err.log; wc -l /tmp/err.log
0 /tmp/err.log
```
✅ 完全干净。

## 6. 待优化项（不阻塞，下一轮再做）

| 优先级 | 项 | 简述 |
|---|---|---|
| 高 | P1-8 CrawlService 长生命周期内容退化 | obsidian 第 11 次访问只返回 185 chars（首次 36KB）。`cleanup_after_n_calls` 或定期 reset browser context |
| 中 | search unwrap 慢 | 现在 unwrap 一条 redirect 要 5s。可以加 LRU 缓存（多轮同 query 复用）或返回原 URL + 让 fetch 时再 unwrap |
| 中 | code.claude.com 超时抖动 | 修复前一次 25s ok，修复后一次 120s 超时。Playwright `magic` + `simulate_user` 强 fallback 慢，需要更精细的 site_tuning |
| 中 | weixin / mp.weixin 失败 | 微信 webfetch 抖动，疑似需要特殊 cookie/UA。当前用通用路径 |
| 低 | ChatGPT share 内容只 301 字符 | selector 不再超时，但 ChatGPT 服务端可能限制了未登录访问。需要 cookies_json 或 Persistent profile |
| 低 | 金标准 9/14 没有自动快照对比 | 加 `pytest -m golden` + nightly CI |
| 低 | release.yml 没有 golden gate | 当前发布只 lint + twine check，不阻塞 P0 进 PyPI |
